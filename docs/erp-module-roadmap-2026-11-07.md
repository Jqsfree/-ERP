# ERP 模块架构审查与两模块验收计划（2026-11-07）

> **不是**完整 ERP 发布证明。业务闭环与交付状态按仓库实测证据判断，任何 Android 真机未执行测试均为“待验”。

## 现状

首页 8 个入口，原本只有销售、客户、产品产生可持久化的业务数据。旧的“销售出货单”实际上只生成销售应收，没有真实出库流水；此名称不能替代出库动作。供应商、采购、库存、退货、费用收入原本仅为静态占位。独立于首页的付款/备份属于销售流程/系统能力，不是两个完整业务模块。

## 自顶向下业务依赖

```text
主数据           客户 / 产品 / 供应商
商业承诺         销售订单 / 采购订单
实物流转         采购收货 -> 库存流水 -> 销售出库 -> 销售退货
账务凭证         采购发票/应付、销售开票/应收、独立收款/付款
管理与核对       费用收入、日结对账、权限、审计与备份恢复
```

采购订单 = 对供应商的承诺，不等于收到货，也不产生供应商应付；采购收货必须独立验证数量、仓库和单位；采购发票才确认应付。销售订单与出库同样分离。参考 ERPNext 官方 Buying / Procurement Cycle 角色划分。本项目保留业务差异，不复制其代码。

## 批次 1 的数据契约

- `suppliers`：唯一名称、联系人、地址、备注、启用状态，保留已生成采购单历史。
- `purchase_orders`：编号 `CGYYYYMMDDNNNN`、供应商身份/联系方式快照、日期、金额、`ordered/cancelled` 状态。取消不物理删除。
- `purchase_lines`：产品 FK 与型号规格快照、米数/门幅、明确独立的**采购单价**及按行四舍五入的金额。
- 业务接口 `ProcurementStore` 与 `SalesStore` 分开。UI 只负责验证并调用操作，数据一致性在 SQLite 事务中重新验证。
- Schema v3 在原 v2 库上仅新增表和索引。原 `customers/products/sales/payments` 数据原封不动。
- 备份升级：新的 v3 存档必须包含采购表；历史 v2 存档恢复时新增采购表为空；不得丢弃原账务数据，也不得静默覆盖设备现有数据。

不承诺：采购订单创建后自动入库、收货、应付款、付款，或库存余额；这些由后续独立用例执行，避免虚构账务。
