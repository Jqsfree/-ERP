# MVP 收尾与验收契约（2026-11-07）

> **立即冻结新业务模块开发。** 本文以 `main@078a44b` 与 `docs/prd.md` 已定义的 P0 销售闭环为依据。
> 当前自动化 CI 全绿并不等于真实手机可用；本文只定义收尾的业务边界、门禁、验证输出，不预先声称测试成功。

## 一、MVP 的唯一任务

在 **一台 Android 手机、无网络、单店单用户** 的条件下，让软装店员从 **客户与商品建档 → 输入米数和门幅 → 出具准确销售单 → 保存与后续收款 → PDF 分享/打印 → 重启后找回数据 → 离机备份/空库恢复** 完成一笔可复核的业务。

这是一款 **离线销售开单 MVP**，不是要在发布前做完采购会计、供应商应付、银行对账或整套 ERP。已有采购、库存、出库、退货、日结代码保留，但**不新增、更不将它们设为 MVP 阻断项**；未经过真实设备验收的扩展模块，不能向用户承诺已经可投入经营。

### P0：必须真正可用

| 编号 | 真实操作（输入→动作→输出） | 合格标准 |
|---|---|---|
| M01 | Android 实机首次安装并打开 | 无崩溃；App 身份、桌面名称、图标可识别；断网可启动 |
| M02 | 用系统中文输入法新增客户、产品 | 光标、中文键盘、粘贴、删除、滚动、返回均可操作；持久化后可查询 |
| M03 | 对同一客户开 1 行/多行销售单 | 米数、门幅、逐行四舍五入、优惠、首收款、单号正确；重复点击不产生双单 |
| M04 | 杀进程并重开 App | 客户、产品、销售历史、草稿、金额和未收款不丢 |
| M05 | 后续补收款并查看客户欠款 | 整数分核账一致、超额收款失败且原金额不变 |
| M06 | A4 中文销售 PDF；系统分享/打印 | 中文正常、10 行及跨页无裁剪；实际接收端能打开、保存，打印预览可用 |
| M07 | 两份 CSV（销售单/明细）导出 | Excel/WPS 正确显示中文与数值；不把整单金额重复记入每条明细 |
| M08 | 创建加密 `.kberp` 并**保存到设备外** | 文件在分享目标能独立找到；错误密码/被改文件被拒绝 |
| M09 | 在另一测试安装/空库导入备份 | 客户、销售、收款、草稿等逐项一致；非空库拒绝导入且数据保留 |
| M10 | 已安装版本原地升级（不卸载、不清数据） | 原账、订单号和收款完整保留；迁移没有错误 |
| M11 | 可重复打包安装的 Android 工程 | 审核后把必要 `android/` runner + Gradle Wrapper 纳入版本控制，固定包名/版本和构建步骤；Debug APK 与受控签名安装包身份一致 |
| M12 | MVP 回归报告与可安装交付 | 同一 Git SHA 的 locked dependencies、Flutter tests、analyze、Android APK 构建全部成功；手机实测报告有日期/设备/结果/证据 |

以上是 **可接受内测 MVP 的完成定义**，不是等待未来再加功能的愿望清单。暂不要求上架 Play 商店或多设备在线同步；应用签名/升级与保护真实数据仍必须可复核。

### 明确不继续开发

- **不做第五批“采购发票/应付 + 供应商付款/核销”**，不继续顺序扩展 ERP 模块。
- 暂不增加更多表、字段、同步、权限、角色、多店、云服务、财务总账、真实银行 API、复杂的供应商或采购退货流程。
- 已有采购/入库/库存/出库/实物退货/费用/日结代码不删除；只修复会导致主应用崩溃、数据损坏或错误暴露的 P0 缺陷。
- 不因“测试数量增加”“CI 又绿一次”就宣布 MVP：最终决定依据 **M01–M12 的真实用户操作输出**。

## 三、执行顺序：只做收尾，不开新业务批次

**P0-A 版本工程定型（实现/验证）**

- 提交版本受控 Android Runner、Gradle Wrapper、manifest、package id、最低 Android 支持范围、应用名称等；确保 `.fvmrc` + `pubspec.lock` 和 CI/Ubuntu 同版本。私钥、keystore、真实密码和本地 SDK 不入库。
- 用同一提交在 Ubuntu / CI 生成调试 APK；检查签名、应用 ID、版本号和安装/升级路径。需要签名发布时使用本机/CI secrets 而不是写入仓库。
- 形成安装/升级步骤、产物 SHA-256、日志和可回滚约束；禁止通过卸载重新安装“验证升级”。

**P0-B 真机核心体验/数据（实现/验证）**

- 先复现并修复中文系统输入法与客户、产品、销售表单问题，检查焦点、键盘遮挡、真实点击、多次快速确认。
- 端到端人工走 M02–M07，记录销售金额、重启和持久化对账、PDF/CSV 实际导出结果；软件断网也可操作。
- 以真实手机执行 `integration_test/storage_device_test.dart` 的临时数据库自动测试，并补齐系统文件选择器与打印/分享的人工证据。该测试 **不能替代生产数据库的备份恢复演练**。
- 将密文备份分享至设备外，在安全的**全新空库**环境恢复，同步核对销售金额、已收款/欠款、客户/产品和历史单号；非空库保护用独立测试库检验。

**P0-C 发布候选冻结**

- 全部 M01–M12 记录为 `pass`、附上命令输出/截图/数据比对结果；发现缺陷只修 P0 缺陷，并重新运行相关回归和构建。
- 出具 `mvp-acceptance.md`（设备型号、Android 系统版本、Flutter SHA、App SHA、检查人、逐项通过/失败/阻断原因）。
- 内测 MVP 版本号与安装包、变更摘要、已知限制和安全备份说明成套交付；`main` 或发布 Tag 指向同一已验证代码。
- 对已实现但不属于销售开单 MVP 的功能标注试验性质；不要把它们写成“已商用验收”。

## 五、验收决策

- **合并代码**：本次以后只允许 MVP 缺陷修复、Android 构建版本化、数据安全/恢复、测试、文档与发布产物改动；每个 PR 合并前要有对应自动化验证。
- **MVP 可内测**：M01–M12 全部通过，或逐项提供经过用户明确批准且不会损害数据的受限验收豁免。
- **MVP 不可交付**：关键中文输入无法使用、销售金额/欠款错误、真实打印分享失败、唯一副本无法恢复、重装/升级丢失数据、运行时崩溃或未验证真实设备时。

后续重新讨论扩展功能的唯一触发条件是 **MVP 已有可安装、可复核、用户能独立完成交易的版本**，而不是再做两模块一批。
