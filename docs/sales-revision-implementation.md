# 已确认销售单修订：实现约束与待解决问题

本文件保留前期约束与计算基础记录；下方“待确认/尚未完成/v7”均为当时状态。用户现已确认换客/改日期、超收先待退款及实物退回前不改库存，已落地的v8模型与当前实现以 [第二阶段交付记录](phase2-sales-revision.md) 为准。

当前数据库为 v7（新增客户余额流水，尚未接入销售结算）。`sale_dispatch_lines.sale_line_id` 引用 `sale_lines.id`；库存流水按出库和实物退货明细计算，备份导入会校验这些关系。直接删除、替换或修改已出库原销售行会破坏历史语义或备份校验。当前 `payments` 只允许正额，日结按销售收款及独立资金流水计算，没有销售退款流水。

实施时应在单事务内保留原始交易及履约明细、追加修订版本和差额记录，确保新旧数据库备份均能校验并恢复；读单、应收、导出和出库必须统一使用当前有效版本，已发生的出入库保持引用原始来源。待退款不等于已退款，待退货不等于已入库。退款确认必须与日结资金统计一致，并保留实际退款日期、渠道、金额及来源；实际退货仍引用真实出库。

以下情况必须在实现与测试中明确处理：连续修订导致待退款或待退货增减、部分退款或退货后再次修订、更换客户时已收款与退款债务归属、同一产品多行和更改门幅、已日结日期、重复请求、旧备份升级与恢复。没有完整规则和针对性回归前，不开放改单入口，不变更生产数据库 schema。

## 已确认的客户变更规则

用户确认：销售单更换客户时，原客户已付的款项继续归原客户，新客户重新付款；不得将原收款隐式转移到新客户。应在改单前展示原客户应退余额和新客户应收，并保留收款时客户身份及实际退款记录。现有 `payments` 仅引用销售单，无法独立表达收款时客户，现有 `customerOutstanding` 又按销售单当前客户汇总；因此只修改 `sales.customer_id` 会把原收款错误转移，禁止采用此方案。

现有备份校验还要求每单累计收款不超过应收；支持待退款后需要在版本化备份中改为验证收款、退款和待退款之间的守恒关系，并兼容 v2–v6 快照。日结中退款须按实际发生日期和渠道计入支出，不修改已冻结的历史日结。

## 第二阶段启动：已落地的计算基础

- `SaleLine.id` 从 SQLite 原行读取；新行为空，原行稳定ID可用于明确修改/删除，不能通过商品ID或列表位置猜测身份。未更改数据库结构。
- `SaleRevisionPreview` 为只读领域计算：验证原行身份、拒绝重复及跨单行，按已有金额规则重算小计、优惠和正负差额，保留逐行前后对照。商品/规格/门幅变化会明确标为实物身份变化；这仅是识别，不代表已确认退货策略。
- 不生成退款、余额、出入库流水，不覆盖原销售事实，不接入现有未经确认的 `SaleSettlement` 结算假设。
- `test/sale_revision_test.dart` 覆盖同商品不同原行、删行新增、改价减量、未/部分/全额收款预览、非法参数与数值溢出、真实SQLite读取和重启、重复预览全表不变。

当前尚未完成：持久版本快照与历史查询、修改保存事务、差额凭证、改单UI及已收款/已出库后的生产处理。第二阶段不能标记完成。

待用户确认的本阶段最小规则：

1. 是否允许更换客户和修改销售日期。
2. 超收是否先形成待退款，由用户选择实际退款或转余额，不自动转入。
3. 已出库行减量/删除是否先形成待退货、不动库存；已出库行换商品/门幅是否作为原行退货与新增行处理。

确认后方可定稿持久化模型。拟采用追加版本快照、稳定原行关联、预期版本校验与请求键幂等；版本/结算/履约写入和备份兼容必须集成后才开放改单按钮。
